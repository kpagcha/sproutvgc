# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

sproutvgc is a competitive Pokémon dex (in the spirit of the Smogon and Showdown dexes): a Vue 3 + TypeScript + Vite SPA, deployed to GitHub Pages at `https://kpagcha.github.io/sproutvgc/`. It's organized in four areas, in the order Meta (first, as what sets the site apart), Tools, Quizzes, Dex (`src/lib/areas.ts`; the plan behind them is in the untracked `notes/competitive.md`): the **dex** (`/dex`), what exists in the regulation, with a list page and an entry page per category: Pokémon (`/dex/pokemon`, `/dex/pokemon/:id`: sprite, types, abilities, stats, evolutions and forms, moves, and a link to its meta page (the meta's pages don't link back to the dex)), moves (`/dex/moves`, `/dex/moves/:id`), abilities (`/dex/abilities`, `/dex/abilities/:id`), items (`/dex/items`, `/dex/items/:id`) and conditions (`/dex/conditions`, `/dex/conditions/:id`: statuses, volatile effects, side and field effects, weather, terrains), plus the types (`/dex/types`, `/dex/types/:type`); ## Commands

```sh
npm run dev         # dev server (base path `/`), also on the LAN for testing on a phone
npm run build       # marker check + vue-tsc type-check + production build, in parallel (base path `/sproutvgc/`)
npm run lint        # ESLint (lint:fix to autofix)
npm run format      # Prettier (no semicolons, single quotes, 120 columns)
npm run gen-data    # regenerate src/data/generated/ (add `-- --update` to repin the sources to their latest commits, `-- --update-smogon` for Smogon's month alone, `-- --update-tournaments` for the tournaments alone, `-- --offline-tournaments` to make no requests for them, leaving out any event not already generated or cached whole)
npm run live-tournaments  # read the official tournaments under way into src/data/generated/live/ (gitignored; the deploy runs it before building)
npm run check-text  # check the markers in our curated text (also part of `build`)
npm run bench-search  # time the search's matching over every language's names, at 1×, 10× and 50× the dex (`-- 1 100` for other scales)
```

When a regulation changes, follow the checklist in `docs/regulation-change.md`.

The `justfile` wraps these for the user (`just dev`, `just dev-profile`, `just build`, `just live-tournaments`, `just preview`, which builds and then serves the production site at `http://localhost:4173/sproutvgc/`, `just gen-data`, `just check-text`, `just bench-search`); keep it in sync when scripts change.

There is no test suite, and none should be added. Verify changes with `npm run build` plus checking the app in the browser. The pre-commit hook (simple-git-hooks + lint-staged) runs `eslint --max-warnings=0` and Prettier on staged files, so any lint warning blocks a commit. CI (`.github/workflows/deploy.yml`) runs lint + build on every push to `main` and deploys; it also runs every half hour from Friday to Monday (UTC), reading the tournaments under way first (`npm run live-tournaments`, as every run of it does), and deploys then only when what it read changed (its hash kept in the Actions cache with Limitless VGC's responses). GitHub Pages has no SPA fallback, so the build (`scripts/seoPages.ts`, a Vite plugin) writes `404.html` (the app, so any deep link works) and, for every page meant to be found (the areas, the dex's lists, types and every entry the regulation has, the rankings and the meta page of every Pokémon in the default dataset, the tournaments and each one's standings, Pokémon and rounds, the working tools, the credits; not the settings nor what's coming soon), a `<path>/index.html` of its own, served with a 200: its English title, description and keywords as `App.vue` sets them, a canonical URL (with the trailing slash GitHub Pages redirects folders to; the router drops it), structured data with breadcrumbs, and `sitemap.xml` listing them all. A new page to be found goes in its list; routes give the document a title and keywords of their own for search with `meta.headKey` and `meta.keywordsKey`. `.github/workflows/usage-stats.yml` runs `gen-data --update-smogon` on the 2nd and 9th of each month and, when Smogon has published a new month, opens a pull request with it; `.github/workflows/tournaments.yml` runs `gen-data --update-tournaments` every Tuesday and opens one when the tournaments changed.

## Architecture

- **`src/data/types.ts`**: the Gen 6+ type chart, stored as a sparse attacker→defender map (pairs left out are 1×), exposed through `chart(atk, def)`. `TypeIcon`'s badges use the Bulbagarden Archives glyphs (`src/data/typeGlyphs.ts`), as do `CategoryIcon`'s move category badges (`src/assets/category-icons/`). `TypeId` is the canonical type key everywhere.
- **Generated data (`src/data/generated/`)**: written by `scripts/gen-data.ts`, never edited by hand (nor are the sprites it writes, below). It loads Pokémon Showdown's own code (through jiti) from a sparse checkout of its GitHub repo at the commit pinned in `scripts/sources.json` (cached in `node_modules/.cache`), applies the Champions mod and the rules of the VGC format for `VITE_REGULATION`, and derives availability from the regulation's legal Pokémon (an ability is available when one of them can have it, a move when one of them learns it and the game has it, an item when the game has it, a Pokémon when the format allows it). English names are Showdown's; every other locale's come from PokéAPI's CSVs, also pinned, at the language identifier `scripts/languages.ts` gives it (none for now; Spain's Spanish would be `es`); nothing in the script is specific to a language. `scripts/overrides.ts` fills in by hand, per locale, the names PokéAPI doesn't have yet (it lags new releases), the ones it has outdated (renamed since), and names for entries the games don't name on their own (Showdown's per-mask Embody Aspects). Pokémon names are provisional: the species' official name plus the forme as Showdown labels it ("Garchomp (Mega-Z)", "Raichu (Alola)"), since PokéAPI's official forme names are patchy. The script stops and lists any name an entry of the regulation is missing. Bulbapedia is a place to check names by hand, never a data source: its text is CC BY-NC-SA. Use GitHub, not the npm packages (`pokemon-showdown`, or `@pkmn/dex`, `@pkmn/data` and `@pkmn/mods`): they ship the Champions mod but lag a regulation behind it, and the `@pkmn` ones have no format rules. The output is JSON, one entry per line: for abilities, moves, items and Pokémon, `<category>.json` (every entry and whether the regulation has it; for available abilities, moves and items also Showdown's `short` and `long` descriptions, verbatim, resolved for the Champions mod by its own `loadTextData`, which prefers the mod's text and falls back from either description to the other: the source our own descriptions are written from, never shown as is), `<category>.names.<locale>.json` (names of the available entries only, the only ones shown) and, for moves, items and Pokémon, `<category>.data.json` (what their pages show of each available entry: a Pokémon's types, base stats, abilities (in slot order, not marking the hidden one), forms and evolutions, its cell on the icon sheet; a move's type, category, power, accuracy, PP as Champions computes it, priority, target and flags; an item's kind, Megas and category (what it's for: Mega Stone, offense, defense, Speed, field or utility, `src/data/itemCategories.ts`, derived by `scripts/itemCategories.ts` from the handlers Showdown's code gives it and the code that checks for it, a few set by hand; the script stops on an item it can't place); typed in `src/data/pokemon.ts`, `moves.ts`, `items.ts`); `pokemon.learnsets.json` (each legal Pokémon's moves, loaded on demand by `loadLearnsets`), `abilities.holders.json` (the legal Pokémon that can have each available ability, for its page), `conditions.json` (every condition something the regulation has causes, by Showdown ID, with those moves, abilities and items: declared on moves, or found in their code by `scripts/conditions.ts`), `available.json` (just the IDs of the available entries, per category, conditions included: the compact part the app needs at run time), `sprites.json` (the icon sheets' layout), `natures.json` (the natures' names in every locale, by Showdown ID, read through `natureName` in `src/data/natures.ts`), plus `source.json`, which records the commits, pages and format it all came from. **Sprites** come from Showdown's server (`scripts/sprites.ts`, through `sharp`): its Pokémon and item icon sheets trimmed to the regulation's entries, as lossless WebP, in `src/assets/sprites/` (drawn by `PokemonIcon` and `ItemIcon`, with `src/lib/sprites.ts`), and each legal Pokémon's gen5 sprite in `public/sprites/pokemon/` (`spriteUrl`; a Pokémon Showdown hasn't drawn yet has `noSprite` and its page shows its icon). They aren't versioned: `sources.json` keys their cache by the date of the fetch (`sprites`), and pins the commit of Showdown's client whose icon table places formes on the sheet (`client`). App code imports the full `<category>.json` files only with `import type` (for the ID types, at no bundle cost); Vite's `json.namedExports: false` keeps each JSON module a single `JSON.parse`.
- **`src/data/dex.ts`**: the dex's categories (conditions, moves, abilities, items, Pokémon, plus `group` for groups of effects) with their IDs (abilities, moves, items and Pokémon from the generated data; conditions from `src/data/conditions.ts`, the curated list of the ones with an entry of their own, each with its subkind and, when it differs, Showdown's ID: a condition is available when `conditions.json` has a source for it; groups list the IDs referenced so far), and `Ref`, the reference to an entry: a `kind` plus an `id`, as IDs are only unique within a category (Electric Terrain is a move and a terrain). Data mentions entries through the constructors (`move('soak')`, `condition('sun')`), never bare strings; `available()` hides what the current regulation doesn't have, from the generated data; nothing about availability is maintained by hand. Render a ref with `<DexRef :to>` (on the meta's pages `<DexRef :to meta>`, which leads to the entry's meta page where its category has them, `META_PAGES` in `src/lib/links.ts`, so a new category of meta pages goes there, and the meta's links to its entries follow; on the data the page provides as `META_LINKS`, if any: a tournament's pages and a build's give their regulation's (`regulationSnapshot`), so their entries open on the data they were played on, the data button then marked as not the latest), which is plain text until its category is registered in `PAGES` (its route's name, and the parameter that takes the ID: `id` unless given, `type` for the type pages; every category but groups is registered), and from then on a link. `src/data/typeinfo.ts` holds the interactions beyond the type chart, made of refs.
- **Meta (`src/data/meta.ts`)**: what players use, as snapshots from one source or another (Smogon's Showdown stats, the game's Battle Data, tournaments), each turned by an adapter in the generator into the one shape typed there and written to `src/data/generated/meta/` (`index.json` lists the snapshots, `<id>.json` holds each one's data by Pokémon, `loadMeta` loads it on demand, and `ranks/<id>.json` its ranks alone, `loadRanks`, for a page that needs no more of it: a tournament's standouts). The only adapter so far is `scripts/smogon.ts`: Smogon's stats for each regulation's format, every month of it, pinned per regulation as `smogon` in `sources.json` (the current regulation added on its own; `--update` and `--update-smogon` pin every month there is), a snapshot per month and rating cutoff (`smogon-mc-2026-09-1760`, `-1630`, `-1500`, `-0`). Past regulations stay listed there and keep being generated, as their history (and the trends run on across a family of them: M-C's first month is against M-B's last, `withPrevious`, its "since" naming the regulation, `sinceLabel`): the current regulation's stop on any name the dex doesn't have, past ones' leave it out; each past regulation's legal Pokémon go in `meta/rosters.json` (`pastRoster`, the speed tiers' "every Pokémon" with its data shown). Tournaments come from Limitless VGC (`scripts/limitlessVgc.ts`: the official events of each regulation, from limitlessvgc.com's lists, pinned by their number there as `limitlessvgc` in `sources.json`, and each one's standings, team lists and matches from the undocumented JSON its standings site loads, 4 at once and at most 8 a second, about a thousand a Regional (one per player's team list), made once: an event generated in the current shape (`FORMAT`) is kept from its committed files; RK9's terms forbid scraping), not as snapshots but as each event's teams: `src/data/generated/tournaments/index.json` lists the events (type, date, players, Day 2's and the top cut's, rounds, who won with what), `<id>.json` each one's standings by placing, its whole field: the player, their record, whether they made Day 2 and the top cut and when they dropped, and the six they brought (Pokémon, item, ability, nature, moves; no stat points, which team lists don't have; the Pokémon alone without a team list), `<id>.rounds.json` its rounds' matches, `usage.json` every event's Pokémon in a few numbers (teams with each by day, best placing, its teams' matches won and lost), `builds/<regulation>.json` (`mc`) each regulation's builds, every event's teams added up (each Pokémon's sets from team lists and its 10 most common whole builds, for its meta page whatever data it shows), and `upcoming.json` the events still to come, from its list of them (`UPCOMING`, those started more than a few days ago, live or generated since left out); the events under way, and those over but not generated yet (within 10 days of their start), are read before each deploy by `scripts/liveTournaments.ts` (`LimitlessVgc.underWay`, `liveEvent`: the standings site's list of events, its standings, rounds so far and the team lists out so far, its own cache folder `api/live/` but for team lists; what the dex has from the generated data, no Showdown; matched to `upcoming.json` by city and date for their name and number) into `src/data/generated/live/` (gitignored), the same shape plus `live` (round of rounds, when last updated, whether over, who leads), a match still being played a 1 after the result (`pending`): the app shows them with the rest (`LIVE_EVENTS`, their pages as any event's, `eventOf`; the standings' Day 1 not folded when it's all there is; the Pokémon tab saying no team list is out yet, or that what it counts is partial) but never in `EVENTS`, so nothing that adds events up (trends, baselines, builds, win rates) counts them until the weekly refresh generates them for good; the app adds up whichever events are picked (`src/data/tournaments.ts`, `loadTournaments`), each set of them and of whose teams count (all players, Day 2, top cut) a snapshot made on demand (`tournaments-mc` every event of M-C, `tournaments-mc~445.446@day2` two of them, Day 2's teams; `findSnapshot`), not shown as meta data for now (left out of `VITE_META_SETS`: the tournaments' pages are their own, and their links to the meta lead to the regulation's data, `regulationSnapshot`: its latest dataset, the default for the current one, so its URL stays bare), with no spreads, Speeds, brought nor trends but each Pokémon's whole builds (`builds`). `VITE_META_SETS` in `.env` picks the ones the app shows, by ID or pattern (`smogon-*-1760`), so switching cutoff or source is a setting. The reader picks one with `MetaDialog`, on any page that shows meta data (a button naming the snapshot's regulation alone, its dataset (what one source observed over one period for one regulation) and subset in the card it opens: `MetaCard` in a dialog over the page on any screen (`ModalDialog`), scrolling when taller than it: the regulation, then a plain list of its datasets (each labeled by its source and period, whatever the period: Smogon's happen to be months), then its players, datasets grouped by `metaDatasets`), and it's the one every page shows from then on (`selectedSnapshot`, `selectSnapshot`, remembered under `sproutvgc.metaSet`, a pick of the latest dataset as `latest:<subset>` so it follows new ones; the default is the current regulation's latest dataset; the page's URL says which as `?meta=<id>` when it isn't the default (`useMeta`), so a link opens on its data, which every page then shows, while starred setups, the speed pages' "as last left" and their Reset all leave it out (`withoutMeta`); pages read it, and its data, through `useMeta`, which, another one picked, keeps the page on the data it shows, faded (`loading`), until the new one is in and a frame has painted the pick, `MetaDialog`'s icon pulsing meanwhile (`metaLoading`)); on the dev server, a dev-only section of the settings page (`src/dev/MetaDevTools.vue`) overrides it in the browser (`setActiveSnapshots`, saved under `sproutvgc.dev.metaSets`), left out of production builds. The app never tells sources apart, only checks a snapshot's `capabilities` (`has`) and shows what's there; with none there's no meta. Every number shown is labeled with its snapshot (`metaLabel`), and what covers every player whatever the cutoff (`unweighted`: Smogon's brought counts) says so. The credits page credits the shown snapshots' providers. The plan and the sources are in `notes/competitive.md` and `notes/usage-stats.md`.
- **`src/lib/`**: pure logic with no Vue components. `typecalc.ts` (effectiveness, defensive profiles, coverage, multiplier formatting/CSS classes), `quiz.ts` (builds the quiz cards: "pick the multiplier" and "tick all types that apply"), `srs.ts` (SM-2 scheduling with Anki-style learning steps counted in answers rather than time; the type quiz's deck is saved to localStorage under `sproutvgc.quiz.v1`, another quiz's under a key of its own), `motion.ts` (shared `SPRING`/`FADE`/`PRESS` animation settings), `stats.ts` (Champions' stats: base plus stat points plus 20, times the nature; HP plus 75, no nature; and the benchmarks that mark a stat's range, on the speed tiers' ladder), `speed.ts` (natures' effect on Speed, battle modifiers, and the table of the items and abilities that change it, with their multiplier, condition and the modifier that applies it (so a boost chip on the speed tiers counts a modifier its boost already is once, and leaves out what it can't be with: Unburden or an Iron Ball with a Choice Scarf on everyone; and a Pokémon whose item is fixed, a Mega's Mega Stone or Ogerpon's mask (`itemBound`), has none of the items nor Unburden, on both speed pages: `withoutItems`, `togglesFor`), kept by hand: `npm run gen-data` lists any the regulation has, by Showdown's `onModifySpe`, that it lacks; the speed tiers turn the meta's `speeds`, Speed investments by stat points and exact nature, into Speeds with the base stats).
- **`src/views/`**: one lazy-loaded view per route (`src/router.ts`). Route `meta.titleKey` sets the document title; `App.vue` titles entry pages after the entry. Shared pieces: `MoveTable` (a sortable, searchable table of moves; on a Pokémon's meta page with each move's share of its sets, `shares`, sorted by it, and without PP or filters, `noPp`, `noFilters`), `PokemonChips`, `RefInteractions` (an entry's type interactions, from `typeinfo.ts`), `SortHeader` with `useSort`, `MoreToggle` (a list's first few until unfolded; every folded list's unfolding remembered for the visit, in memory, by a key naming it, `useUnfolded`, so a page come back to finds them as left). Entry pages title themselves with `EntryTitle`, whose star adds the entry to the reader's favorites (a Pokémon's meta entry too, `meta`, a favorite of its own: "Meta entries") (`useFavorites`, saved to localStorage under `sproutvgc.favorites.v1`), listed on the home page (`FavoritesPanel`, cleared whole or a category at a time) and, beside a page's way back (`App.vue`'s back row), those of its kind in a drop-down (`FavoritesMenu`: an entry page's category, the speed pages' starred setups; on phones, its star alone), and records the visit for the home page's recently viewed (`useRecent`, saved under `sproutvgc.recent.v1`, `RecentPanel`, folded until unfolded and then as last left, `sproutvgc.recent.open`) (the recently viewed, this and the speed pages' `PageHistory`, are off for now, nothing recorded nor shown, by `RECENT_ON` in `useRecent.ts`; the code is kept to bring them back); both draw entries with `EntryChip`. Pages whose view is in their URL go among the recently viewed too, as they were left (their route's `meta.recent` says what counts as one visit: one per page, a comparison per pair; `router.afterEach` records them), drawn with `PageChip`. The speed pages, being complex, have a tour on the first visit (`useTour`, driver.js, its popover styled in `retro.css`: steps pointing at the first of their selectors on screen, those with none left out), not shown again once dismissed or done (`sproutvgc.tour.<page>`), their guide to reading them (what each part and option means; no help section besides), taken again from the Footprints icon at their heading's end (`TourToggle`). Those pages' setups can be starred too (`SetupStar` by their heading: what their route's `meta.setup` keeps of the URL, leaving out what's only a moment of it, such as the Pokémon found), several per page, listed among the favorites with `PageChip`. The Pokémon pickers (`PokemonPicker`) list, while their search is empty, the Pokémon picked lately in any picker with `recent` (every one so far), then the reader's favorite Pokémon, each group showing its first 8 with a link to all and folding away, then every Pokémon (`usePickerGroups`: the picks saved under `sproutvgc.picker.recent.v1`, the groups folded under `sproutvgc.picker.folded.v1`). The home route waits for the dex's names only when there are favorites or recent visits (`meta.dexNames` can be a function). A route can start the data its page loads first as navigation does, beside its code and those names, rather than once the page is set up (`meta.prefetch`: a tournament's pages, its standings and rounds, and on its Pokémon tab the usage before and the ladder's ranks, which the Standings tab doesn't load). The search (`useSearch`) finds the site's pages by name too (`pages`: an area's, or a section's by its label or title), on the home page and the dex's. List pages take the home page's search as `?q=`. Every list's search is one box (`FilterSearch`): its text searches the list (by name, or by what its entries do too; from two characters, `MIN_CHARS`; the list and the options following once the typing pauses, `SETTLE`, or at once when emptied, on Enter or leaving the box), and finds the terms to filter it by (`src/lib/searchTerms.ts`: a type, an ability, a move, an item, a Pokémon, or what isn't a dex entry: a move's category, tag or reach, an item's category, a condition's kind; what passing one means is the list's), each offered with how many of the list it'd leave (`useTermPicker`, `TermOptions`), the placeholder saying what it searches by; the term highlighted shows the list with it added, faded (`preview`). Plainly the filters picked are chips under the box, all to pass; in the advanced mode (its button beside the box, one choice for the whole site, remembered under `sproutvgc.filters.advanced`, `useAdvancedFilters`; on too when the URL's filters need it) they're groups under it, each joining its filters with AND or OR, the groups joined the same way, any filter negatable, each group adding more from the explicit choices, what to filter by and then the entry, every one of its kind (`FilterGroups`, `FilterAdder`, `termOptions`). They're kept in the URL as `?f=` and `?fm=` (`src/lib/filterGroups.ts`, `useUrlFilters`): the Pokémon list (by type, ability or move, `src/lib/pokemonFilters.ts`), the moves (`MoveTable`'s `filters` model and `kinds`; a move's page links to them by category and tag, older links' `?category=` and `?flag=` still read), abilities (by Pokémon), items and conditions (by category and kind), the rankings and the speed tiers; a meta entry's table and a move's Pokémon keep theirs on the page. View state that should be shareable is kept in the URL query (matchup picks, the selected chart cell) and updated with `router.replace`. Long lists (the dex tables) render hundreds of components, so the ones in their rows are light (and memoized, `v-memo`, so the page's other changes, such as the search's options, don't draw them again; on a `<template>` or inside another `v-for` it doesn't work, so a `dl`'s entries are a `div` each, `display: contents`, and the standings one flat list; a long list growing by many at once draws them a chunk a frame, `useGradualRows`): links are `AppLink`, a functional component around a plain `<a>` with its href resolved once and cached (`hrefOf`/`refHref`, `src/lib/links.ts`) and the router following it (`follow`), rather than a `RouterLink`; `PokemonIcon`, `TypeIcon`, `CategoryIcon`, `DexRef` and `DexText` are functional components too (render functions in `.ts` files, with their styles in `main.css`).
- **Descriptions (`src/i18n/en/<category>.ts`: abilities, moves, items, conditions)**: our own English text, curated from Showdown's (in `<category>.json`; conditions have none, so theirs are written from scratch and have no `source`), with "Pokémon" and markers for references to other dex entries (`{type:flying}`, `{move:taunt}`, `{ability:scrappy}`, `{item:ironball}`) that `<DexText :text>` renders as the entry's name (through `DexRef`) in the reader's language, linked once its category has pages; entries the regulation doesn't have are plain text. Each entry records `source`, a hash of the Showdown text it was written from, and `npm run gen-data` lists the entries whose source has changed since (to revise), the entries not described yet, and descriptions of entries the regulation no longer has. The files have no imports, so the generator can read them. Every other language translates ours in `src/i18n/<locale>/<category>.ts` (none for now), same shape and markers, with `source` the hash of the English it was translated from: `gen-data` lists, per language, the translations whose English has changed since and the entries not translated yet. The app loads one language's descriptions at a time, per category, on demand (`src/i18n/descriptions.ts`: `description(kind, id)`, falling back to English for one not translated yet; routes that show them list their categories in `meta.descriptions`). In text, an entry with a description shows its short one on hover. `scripts/check-text.ts` (part of `npm run build`, so CI runs it) checks every marker, in every language's descriptions, names an entry the dex has and the regulation has, through the app's own `dex.ts`; a new category of curated text needs adding to its `DESCRIBED` list.
- **i18n (`src/i18n/`)**: a small hand-rolled module, not vue-i18n. `en.ts` is the source of truth for `MessageKey`. Other locales are typed as `Record<keyof typeof en.messages, string>`, so a missing key is a compile error. Each locale also exports the official in-game names of the types (`types`), and of the conditions and groups (`names`, typed `Names`, so a missing one is a compile error too); conditions named after their move (`named: 'move'` in `conditions.ts`: Taunt, Tailwind) take its name, and generated categories (abilities, moves, items, Pokémon) get theirs from the generated data for every locale. `refName(ref)` (`src/i18n/refName.ts`) names any entry; the generated names load on demand, one locale at a time (`loadDexNames`), and routes that show dex entries set `meta.dexNames` so navigation waits for them (a new page with `DexRef` needs it too, or its names fill in a moment late). Use `t(key, params)` for `{name}` placeholders, `tSplit` to render a component (e.g. a type badge) in the middle of a message, `tSlots` for several, and `typeName(type)`. To add a language: create `src/i18n/<code>.ts`, add it to `LOCALES` (`src/i18n/locales.ts`, which the generator reads too) and `BUNDLES` (`src/i18n/index.ts`), give its PokéAPI identifier in `scripts/languages.ts`, and run `npm run gen-data`, which lists any names to add to `scripts/overrides.ts` (and, once `src/i18n/<code>/abilities.ts` exists, the ability descriptions left to translate; until then it shows the English ones) (`refName` picks up the new name files on its own). The type-check fails until each of those has the language.
- **Theming**: CSS custom properties in `src/styles/main.css`. Light is the default; dark comes from `prefers-color-scheme` unless overridden by `:root[data-theme]` (set by `useTheme`). The look itself (square ink-outlined surfaces, hard shadows, `TypeIcon`'s and `CategoryIcon`'s flat badges) is `src/styles/retro.css`, on top of `main.css`'s base; its rules start with `:root:root` so they win over components' scoped styles. `index.html` applies the saved theme before first paint. Multiplier colors are the `--m*-bg/fg` tokens, applied through `multClass()`. Components use `<style scoped>` plus the global tokens and utility classes.
- **Animation**: motion-v (`motion.*`, `AnimatePresence`, `layout-id`). Reuse the settings from `src/lib/motion.ts` so all animations feel consistent. `App.vue` wraps everything in `MotionConfig reduced-motion="user"`. Animations that run while a page renders (the page transition, the header's sliding highlight, `NavPill`) animate only `transform` and `opacity`, which the browser runs off the main thread: not motion's `x`/`y` nor a `layout-id`, which it animates on the main thread, so they stall while the page renders (`SPRING_WAAPI` is `SPRING` for the Web Animations API). Pages slow to render (the dex tables) show a skeleton until they're in (`usePageEntered`, `SkeletonRows`). On desktop they're also kept when left (`KeepAlive` over `KeptPage` frames, `src/components/PageFrame.ts`, listed in `KEPT` in `App.vue`), so coming back doesn't render them again; a kept page reads the route's query through `useActiveQuery`, which follows it only while the page is shown, not `useRoute()`. Phones' sliding pages (a `TransitionGroup`) can't hold a `KeepAlive`.
- **Tooltips**: the global `v-tip` directive (`src/directives/tip.ts`, tippy.js) replaces native `title`. `v-tip:group="..."` makes elements share one singleton tooltip that glides between them (used for table cells). Every tooltip shown takes the taps on it (a tap there hides it rather than reaching what's under it: `main.css`, and `tip.ts` ending the touch there, so the mouse events and click that follow it don't land on what's under once it's gone), and on a touch screen tapping what it's of toggles it (`tapToggle`, a tippy plugin for all but those placed by hand; on a screen with no hover, tooltips open on a tap alone, not on the mouse events a touch screen makes up when the page moves under the finger; there, what has one can't be selected, `[data-tip]`, so tapping it twice doesn't select a word).
- **Env files**: `.env` (tracked) holds shared settings the build needs, such as `VITE_REGULATION`; `.env.development` (tracked) holds dev-server-only defaults; a gitignored `.env.local` is for personal overrides. Nothing secret goes in any of them, since `VITE_` values end up in the shipped app.
- **Profiling**: `VITE_PROFILE=true` (`just dev-profile`, or `.env.local`) turns on `app.config.performance` in dev, for Vue's per-component timings in the Performance panel. They inflate durations, so measure speed on `just preview` instead.
- **Dev-only**: the type quiz's dev tools (`src/dev/QuizDevTools.vue`, with `quizSim.ts` and `DevZone.vue`) and the settings page's meta snapshots (`src/dev/MetaDevTools.vue`) are loaded only when `import.meta.env.DEV` is true and are left out of production builds.

## Conventions

- Import from `src` using the `@/` alias.
- Stats are shown as the game shows them: base plus 20, HP plus 75, at no stat points and a neutral nature (`gameStats`, `gameTotal` in `src/data/pokemon.ts`; `statValue` in `src/lib/stats.ts` with points and a nature). The one exception is a Pokémon's dex entry, which shows its base stats, the game's on hover. The data keeps the base stats.
- localStorage access is always wrapped in try/catch, with the app falling back gracefully; keys are prefixed `sproutvgc.`.
- Don't create or trace UI icons; the user picks icons themselves. UI icons come from Lucide (`@lucide/vue`), squared off by the `.lucide` rule in `main.css`.
